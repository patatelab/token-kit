# Token contract

`token-kit check` enforces the rules marked with a rule ID; the rest is process.

## Source of truth

`tokens/tokens.json` (W3C DTCG: `$type`, `$value`, `$description`, references `{a.b}`) is the only manually maintained token-value source. CSS, TypeScript and Tailwind files are generated by `token-kit build` and never edited. New or changed tokens, including references and metadata, need the owner's approval. Equal numerical values never establish semantic fit.

## Tiers and the reference chain

The token guideline defines three tiers on top of the RAW values. Each token references only the next higher tier:

```text
RAW value   #DC2626               16px                Alpha 50
Primitive   color-red-600         radius-500          opacity-500               Figma: Primitive
Semantic    color-error-default   radius-md           opacity-disabled          Figma: Semantic
Component   snackbar-bg-error     button-radius-md    button-opacity-disabled   Figma: Components
```

| Tier | Figma collection | Stored under | Holds | May reference |
| --- | --- | --- | --- | --- |
| Primitive | Primitive | `primitive` | RAW values (hex, rem, ms, numbers), never consumed by product code | nothing |
| Semantic | Semantic | `semantic` | meaning: usage, role, intent, scale; Light/Dark | Primitives only; another Semantic token only via `$extensions.semanticAliases` |
| Component | Components | everything else; family = component | component properties per variant, state and size | Semantic tokens and its own family; other families only via `$extensions.componentContexts` |

The tier model is configuration (`tiers` in `token-kit.config.json`), not code. A token belongs to the first tier whose `match` fits (`roots`, `prefixes`, `paths`, `literal`); each tier says which tiers it may reference. Tier flags: `literals` (may hold RAW values), `families`, `internal` (never read by product code), `themes: false` (inherits themes), `allowPrefixes`, `naming.categories`.

- `TOKEN_TIER_CHAIN` — a reference the tier model does not allow (skipping a tier, a Primitive referencing a Primitive, a Component referencing a Primitive).
- `TOKEN_RAW_VALUE` — a RAW value outside the Primitive tier (except `technicalValues` such as `0`, `none`, `transparent`, and roles marked as technical values, see [Steps](#steps-few-reusable-one-scale-type-per-group)).
- `TOKEN_REF_MISSING`, `TOKEN_REF_CYCLE` — checked across all tokens and every effective theme, including composite values and `var(--…)` inside values.
- `TOKEN_TYPE_MISSING`, `TOKEN_TYPE_MISMATCH` (review) — every token has a type; an alias matches its target's type.

The tier roots `primitive` and `semantic` are groups marked `"$extensions": {"pathSkip": true}`, so they do not appear in names: `primitive.color.blue.500` is referenced as `{color.blue.500}`, emitted as `--color-blue-500` and shown in Figma as `color/blue/500`.

## Naming

Background and terminology: [knowledge/naming-tokens.md](knowledge/naming-tokens.md) (Curtis, 2020).

Names are lowercase and hyphen-separated (`TOKEN_KEY_SYNTAX`); each name part is one group level in the token file. A name is built from these parts, in this order; parts that add nothing are left out, as long as the name stays unique.

| Tier | Structure | Examples |
| --- | --- | --- |
| Primitive | Category-Property-Variant-Scale | `color-blue-500`, `size-200`, `font-family-mark-pro`, `opacity-500`, `radius-500`, `border-200` |
| Semantic | Category-Property-Variant-Scale | `color-text-supplementary`, `color-primary-default`, `color-primary-strong`, `opacity-disabled`, `radius-md` |
| Component | (Group-)Component-Property-Variant-State-Scale | `button-bg-primary-default`, `button-padding-x-md`, `button-icon-primary-hover`, `button-text-primary-disabled` |

**Primitive categories** (RAW values): `color`, `font-family`, `font-weight`, `font-size`, `line-height`, `letter-spacing`, `size`, `space`, `radius`, `border` (width), `shadow`, `opacity`, `elevation`, `breakpoint`, `motion`, `z-index`. Scales are numeric: colour 050, 100–900, 950 with 500 as the medium step; dimensions in hundreds (`size-200`, `radius-500`).

**Semantic categories**: Color, Dimension (`spacing`, `radius`, `border-width`), Effect (`opacity`, `blur`, `shadow`), Typography (`font-family`, `font-size`, `font-weight`, `line-height`, `letter-spacing`), plus `motion`, `z-index`, `elevation`, `breakpoint`. Colour is split into four areas:

- **Brand** (`color-brand-*`): fixed brand colours for logos, graphics, illustrations; largely independent of themes.
- **Usage** (`color-bg-*`, `color-text-*`, `color-border-*`, `color-icon-*`): the concrete purpose in the UI.
- **Role** (`color-primary-*`, `color-secondary-*`, `color-tertiary-*`): visual hierarchy, with `on-<role>` for content on that colour.
- **Intent** (`color-success-*`, `color-warning-*`, `color-error-*`, `color-info-*`): system feedback.

Semantic scales are words: `default`, `strong`, `weak` for intensity, `xs`–`xl` (`sm`, `md`, `lg`) for size, or a purpose (`disabled`, `overlay`). Numeric steps belong to Primitives.

**Component parts**: Group (optional, e.g. Action, Feedback, Navigation; usually left out), Component (`button`, `snackbar`), Property (`bg`, `text`, `border`, `icon`, `radius`, `padding-x`), Variant (`primary`, `secondary`, `tertiary`, or an intent such as `error`), State (`default`, `hover`, `pressed`, `focus`, `disabled`), Scale (`sm`, `md`, `lg`).

- `TOKEN_NAME_STRUCTURE` — a Primitive or Semantic name does not start with a category of its tier (`naming.categories`).
- `TOKEN_NAME_LITERAL` — a name encodes a value, in every tier including Primitives: `raw-`, `literal-`, units (`px`, `rem`, `%`, `ms`, `deg`, `vh` …), hex codes, value prefixes (`number-60`, `factor-0-75`, `angle-180deg`, `negative-…`); numeric scale steps (`spacing-200`, `color-text-500`) outside Primitives.

Primitives use steps, never values. A step is a position on its scale (`radius-500` = 16px, `color-blue-500` = #2B7FFF), not the value itself: `radius-16px`, `size-raw-24px` and `color-hex-2b7fff` are wrong. If a step happens to equal the value (`duration-200` = 200ms) that is fine, as long as the number is the position on the scale.

### Steps: few, reusable, one scale type per group

Background: [knowledge/naming-tokens.md](knowledge/naming-tokens.md) (Curtis 2020, scale modifiers).

A step is a place on a scale that several tokens use. A value that only one token needs is no step.

- **One scale type per group.** Pick the type that fits the value:
  - *ordered* (default): positions in hundreds with gaps for later steps (`radius-500`, `size-200`, `duration-300`);
  - *bounded*: a share from 0 to 100, where the number may be the share (`opacity-40`, `alpha-20`); the default rank scale (`opacity-500`) stays valid;
  - *T-shirt or words* for a short set (`sm`, `md`, `lg`; `tight`, `snug`, `loose`);
  - *enumerated* for a fixed set of options (angles `0`, `45`, `90` …).
- **Few steps.** Values that differ by less than people can see go to the nearest step (for example opacity on a 5-point grid). Aligning a value is a visible change and needs the owner's approval.
- **Single cases are technical values.** A fixed fact of one case (a device screen width, a simulation input, a geometric construction such as `translate(-50%)`) stays in its Semantic or Component role as a RAW value with `$extensions.technicalValue` `{ "reason": …, "origin": … }`. `TOKEN_RAW_VALUE` accepts it. A Primitive never carries a technical value.

```json
"device-frame": { "screen-width": { "$type": "dimension", "$value": "393px",
  "$extensions": { "technicalValue": { "reason": "Screen width of the phone mock-up; fixed by the device.", "origin": "Only reader: the device frame." } } } }
```

- `TOKEN_CONTRACT` — a `technicalValue` without `reason` or `origin`, or one on a Primitive.
- `TOKEN_STEP_SINGLE_USE` (review, off by default) — with `stepMinReaders` (2 suits a grown system), a Primitive read by fewer tokens is a single case: take the nearest step or make it a technical value. Unread steps are options and are not flagged.

## Themes

Theme overrides live under the theme's `root` (default `dark-mode`) with the same logical paths. Only Semantic tokens carry theme overrides. Primitives are theme-independent, and Component tokens inherit the theme of the Semantic tokens they reference.

- `TOKEN_THEME_ORPHAN` — an override without a base token.
- `TOKEN_THEME_OVERRIDE` (review) — a token in a tier with `themes: false` overrides a theme; override the Semantic token it references instead.
- `TOKEN_CONTRAST` — every `contrastPairs` entry meets its WCAG minimum in every theme.

## Reuse and naming

New tokens are the last resort.

1. **Reuse first.** Search the same category for a Semantic token with a fitting meaning. A Primitive step listed in `primaryRoles` has exactly one primary Semantic role; a second Semantic alias of that step in the same category is `TOKEN_ROLE_DUPLICATE`. A token from a foreign category (a radius for a border width) is never reused.
2. **Align, do not tokenise, pattern deviations.** A value that differs slightly from an established pattern is aligned as a visible, approved change.
3. **Names follow the taxonomy** above (`TOKEN_NAME_STRUCTURE`, `TOKEN_NAME_LITERAL`).
4. **Approval of the exact list.** Each new token states tier, name parts, owner, Semantic backing (for Component tokens), Primitive backing, Light/Dark behaviour and consumers. Agents propose; they never self-authorise. `token-kit import` refuses new tokens without `--accept-new-tokens`.
5. Semantic and Component tokens carry a `$description` (`TOKEN_DESCRIPTION_MISSING`, review).

## Proposal: role tokens

*Status: proposal, not yet part of the contract and not enforced. Rule IDs and config keys in this section are proposed names. Source: “Role Token Examples” (owner's PDF, 2026-10-29).*

Semantic tokens name the job an element has in the content, not its value: **Category-Property-Role(-Scale)**, e.g. `color-text-headline`, `color-surface-container`, `color-border-divider`, `space-gap-content`, `size-icon-leading`, `opacity-scrim`.

**Terminology.** "Role" above currently means the hierarchy `primary`/`secondary`/`tertiary` (colour area Role). With role tokens, that hierarchy is renamed **Emphasis** and "Role" means the content job. Decision needed before either is used in names.

**Scale tier.** Many roles share a value, so roles reference an optional `scale` tier instead of Primitives directly. The existing word scales (`spacing-xs`–`xl`, `radius-sm`–`lg`, `opacity-*` steps) move to that tier. It is configuration only:

```json
{ "name": "scale", "match": { "roots": ["scale"] }, "references": ["primitive"], "internal": true, "themes": false }
```

Semantic then references `["scale", "primitive"]`. `primaryRoles` maps Primitive steps to Scale tokens; several roles on one Scale step are intended and not `TOKEN_ROLE_DUPLICATE`.

**Vocabulary.** Roles are a controlled vocabulary per Category-Property, and the same word means the same job in every category (`headline` in `color-text-headline` and in the typography roles). Initial set, to be approved:

| Category-Property | Roles |
| --- | --- |
| `color-text`, typography | `headline`, `subline`, `tagline`, `body`, `value`, `label`, `meta`, `helper`, `placeholder` |
| `color-icon` | `default`, `action`, `status`, `muted` |
| `size-icon` | `default`, `leading`, `trailing`, `status`, `action` |
| `color-surface` | `base`, `container`, `elevated`, `overlay`, `inset` |
| `color-border` | `divider`, `container`, `inset` |
| `space-gap` | `content`, `action`, `section`, `inline` |
| `space-padding` | `control`, `container`, `section`, each with `-block` / `-inline` |
| `opacity` | `disabled`, `scrim`, `overlay`, `hover` |

Proposed config: `naming.roles` per tier, keyed by Category-Property. Proposed rule `TOKEN_NAME_ROLE` (review): a Semantic name whose role part is not in the vocabulary.

**Not roles.**

- Directions: `space-padding-top`, `-left`, `-vertical` say nothing about purpose. Use a role plus a logical direction (`space-padding-control-inline`).
- Numbered positions (`trailing-1`, `trailing-2`): a hidden numeric scale (`TOKEN_NAME_LITERAL`) and an element of one component. Keep them in the component family.
- Components (`color-text-badge` → `badge-text-*`), intents (`status` vs `success`/`warning`/`error`/`info`) and emphasis (`action`, `link` vs `primary`).
- Colour by position (`color-icon-leading`): colour roles describe meaning; positions belong to `size-icon`.

**Opacity by purpose.** System-wide opacity roles (`opacity-disabled`, `opacity-scrim`, `opacity-overlay`, …) replace per-component opacity values. Split by property (`opacity-text`, `opacity-icon`) only where values actually differ.

**Category names.** `size` joins the Semantic categories. One term per pair: `space` or `spacing`, `surface` or `bg` (proposed: `space`, `surface`, because `bg` names a CSS property, not a job).

**Open roles stay open.** A role is added when at least three components need it ([knowledge/naming-tokens.md](knowledge/naming-tokens.md), “Don't globalize decisions prematurely”). `size-illustration`, `size-image` and `size-container` have no roles yet.

## Source audit

`token-kit check` scans `source.roots` for CSS, SCSS, JSX and TSX (tests, stories and generated files excluded).

- `TOKEN_SOURCE_COLOR` — colour literals in declarations and inline styles (error); hex strings elsewhere (review).
- `TOKEN_SOURCE_LENGTH` (review) — px/rem/em literals in spacing, sizing, radius, type and stroke properties.
- `TOKEN_SOURCE_TAILWIND_ARBITRARY` — `bg-[#fff]` (error), `p-[13px]` (review).
- `TOKEN_SOURCE_UNKNOWN_VAR` — `var(--x)` that is neither a token nor declared in the same file (or listed in `source.allowedVars`).
- `TOKEN_SOURCE_TIER_BYPASS` — product code reading an `internal` tier (default: Primitives).

Structural values are not design values: `0` removes a margin, `auto` and `100%` express layout, `transparent` and `none` paint nothing. They are never permission to pick zero type sizes, colours or motion.

A parent never assigns a child component's tokens. Use an approved variant of the child.

## Errors, reviews and the ratchet

Every finding has a stable rule ID, a severity, a subject (token path or file and line) and a suggested action.

- **Errors** fail `token-kit check`. Pre-existing errors can be frozen once in `known-errors.json`; that list only shrinks.
- **Reviews** need a human decision. They are frozen by the shrink-only ratchet in `open-review-ratchet.json` (subject + rule + message, not line). A new or additional review fails.
- `token-kit report` lowers both baselines when findings close and never raises them. `token-kit report --check` (in CI) fails while a closed finding is still listed. Raising is an explicit decision: `token-kit report --accept-new`, with the reason in the PR.
- `token-kit check --strict` fails on every finding and is the only basis for a "fully conform" claim.

## Exchange (export / import)

`*.tokens.bundle.json` carries `format`, `version`, `kind` (`tree`: the DTCG tree; `flat`: path → value map from the Figma plugin), `source`, the portable `config`, `tokens`, optional `baselines` and a SHA-256 `checksum` over the canonical tokens JSON.

Import order: schema and checksum → apply onto the current tree (`--strategy merge` keeps tokens the bundle lacks, `replace` removes them; `--only color,space` limits scope) → full check on the result → diff report. It writes nothing unless `--apply` is given, there are no failing findings and new tokens are approved.

## Audit reports

Larger clean-ups are documented as numbered reports `docs/audits/R001-…`, using `templates/audit-report.md`: result, findings by rule, proposed fixes, decisions needed, and the baseline change afterwards.

## Figma layout

How variables look in Figma is configuration too (`figma` in `token-kit.config.json`, implemented in `src/core/figma-layout.mjs`). The default follows the reference file *ds-3tier-v2* ([R001](audits/R001-figma-ds-3tier-v2.md)): one collection per tier, bold block headings and section headings as divider variables, component names joined after the component (`button/bg-primary-default`), opacity in percent, font weights as style names, shadows as one variable per layer and field, scopes and "hide from publishing" by rule. Headings and dividers are not part of token names; deviations of single tokens are kept in `$extensions.figma.{scopes,hidden}`.
